# 性能：为什么卡、改了什么、多核能帮到哪

## 一、先定位：卡在哪

实测数据（715 个 drawable / 509 个参数 / 5 张 2048 贴图）：

| 环节 | 成本 | 是否可以并行 |
|---|---|---|
| WebGL 绘制（715 draw call + 遮罩离屏） | **主因**，GPU 侧 | ❌ 渲染必须主线程持有上下文 |
| 参数求值（Cubism 内部 + ParamMixer） | 小 | ✅ 可以 |
| 遮罩离屏渲染（2 张 render texture） | **大**，显存与带宽翻倍 | ❌ |
| 关键帧插值 / 拖拽摆动 | 极小 | ✅ 但没必要 |

结论：**瓶颈是绘制，不是计算**。把计算搬去 Worker 收益有限；
真正有效的是「少画」和「画慢一点」。

## 二、已经改掉的（立竿见影）

### 1. 帧率上限 30fps
桌面挂件肉眼看不出 60 与 30 的差别，但 GPU 占用直接减半。
`targetFps = 30`，`tick()` 里按 `1000 / targetFps` 控帧。

### 2. 窗口失焦降到 10fps
用户在 DSH 里去做别的事时，角色不该继续满帧跑。

### 3. 页面隐藏完全暂停
`visibilitychange` → `paused = true`，恢复时补一帧。
最小化窗口后 GPU 占用归零，这是笔电续航的关键。

### 4. 兜底定时器从 33ms 放宽到 66ms
原来的兜底驱动每秒醒 30 次只为判断「rAF 是不是被节流了」。
现在 66ms 一次，且暂停时不执行。

### 5. 修掉重复的遮罩渲染
`maskBufferCount` 从 1 调到 2 是为了支持这个模型的 49 个遮罩，
但它同时意味着 2 张 offscreen render target。
如果换成遮罩更少的模型，应该把它调回 1（`lappmodel.ts` 的 `MASK_BUFFER_COUNT`）。

## 三、还能继续压的

### 按需渲染（收益最大，未做）
完全静止时不重绘。Live2D 有呼吸/眨眼，做不到完全静止，
但可以：**交互结束后 5 秒，降到 15fps；再 30 秒，降到 8fps**。
角色看起来仍在呼吸，GPU 占用降到 1/4。

### 贴图再降档（未做）
现在是 2048 档，共 64MB 显存。如果挂件显示尺寸只有 240~400px，
1024 档完全够用，显存降到 16MB，采样带宽降到 1/4。
只需要跑一次 `node tools/texture-opt/index.mjs <模型目录> --max 1024`。

### 减少 draw call（不现实）
715 个 drawable 是模型本身决定的（美术精度），除非重新导出。

## 四、多核（Worker）能帮到哪，帮不到哪

### 能做的（收益中等）
1. **参数仲裁**：`ParamMixer` 的分层求值、平滑、情绪惯性放到 Worker，
   主线程只收「每帧的最终参数表」（一个 Float32Array，约 2KB）。
   当前参数求值很轻，收益主要是把主线程让出来给渲染。
2. **口型分析**：音频 RMS/FFT 放 Worker，20ms 一个分包，主线程只读结果。
   这条**值得做**，因为音频分析是 CPU 密集且完全可并行。
3. **物理预设**：拖拽摆动的阻尼振荡计算放 Worker，收益小。

### 做不到的
- **WebGL 绘制不能跨线程**。OffscreenCanvas 可以把 canvas 搬到 Worker，
  但 Electron/Chromium 下 Live2D 的 Cubism Core 需要 DOM 与 `document`，
  迁移成本极高且收益不确定 —— **不建议动**。
- 遮罩离屏渲染是 GPU 侧，Worker 帮不上。

### 建议的取舍
先做「按需降帧 + 贴图降档」，这两项几乎零改造、收益最大。
Worker 化留到需要同时驱动多个角色时再做 —— 那时参数仲裁的并行才真正划算。

## 五、怎么验证占用

任务管理器看 GPU / 显存占用，或开发者工具 Performance 面板录 10 秒：
- `frames` 计数应约为 `targetFps × 秒数`
- 暂停后 `frames` 应停止增长（说明可见性暂停生效）
