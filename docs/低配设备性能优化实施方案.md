# 低配设备性能优化实施方案（Windows 4GB RAM / 60Hz 目标）

> 状态：提案 / 待评审。本文定义目标、测量方法、分阶段实现与验收门槛；不代表相关优化已经实现，也不把尚未取得的低配设备实测数据写成事实。
>
> 基线分支：`main`。适用范围：DSH-L2D 插件、Live2D Renderer、Agent 通信链路。

## 1. 目标与边界

目标是在 Windows 10 / 11、物理内存 4GB 的低配设备上，尽可能维持角色前台交互流畅、Agent 消息可靠，并控制插件额外资源开销。

必须区分三个目标：

1. **渲染目标**：前台、可见、交互期间以 60Hz 为目标；帧预算为 16.67ms。
2. **资源目标**：降低插件自身 CPU、工作集、JS heap、GPU 纹理与 RenderTexture 占用，不以牺牲 Agent 通信可靠性换取数字。
3. **可靠性目标**：Agent 事件/动作请求不得因渲染繁忙、Worker 重启、窗口隐藏或队列拥塞而静默丢失。

4GB 是整台机器的物理内存，不是插件可独占的额度。Windows、DSH、Agent、浏览器/Electron、显卡驱动及其他应用共同竞争内存。因此本方案给出插件预算和压力测试门槛，不承诺所有 4GB 机器、所有模型都能无条件 60FPS。GPU 型号、单通道/双通道内存、模型 drawable 数、遮罩数、纹理尺寸和 DSH 负载都会影响结果。

## 2. 已知基线与待核实项

仓库既有《性能与多核方案》记录过一组模型负载：715 drawables、509 parameters、5 张 2048×2048 贴图、约 715 次 draw call，以及 2 张 mask render texture。该记录判断主要成本来自 WebGL 绘制与遮罩离屏渲染，而不是参数计算。

同一文档还记录过 30FPS 上限、失焦降帧、页面隐藏暂停等策略；但后续提交和运行时代码已有演进，**实现前必须以当前 main 的真实代码和新一轮测量为准**，不能把历史文档中的配置直接当作现状。

另有早期进度文档记录过 8192×8192 纹理模型约 592MB 的纹理预算。该数字是特定资源配置的估算，不是插件实测 RAM，也不能直接等同于 Windows 任务管理器中的进程工作集。

### 2.1 第一阶段必须采集的基线

- 插件进程 / Renderer 的 Private Bytes、Working Set、JS heap、GPU 专用/共享内存。
- 冷启动到角色首帧、模型加载耗时、纹理解码耗时。
- 前台静止、连续动作、Agent 高频消息、窗口失焦、窗口隐藏五种状态下的 FPS、帧时间 P50/P95/P99。
- drawable、texture、mask 数量；每张贴图尺寸、格式、mipmap 状态。
- 主线程 Long Task、每帧参数计算耗时、渲染提交耗时。
- Agent 入站/出站包数、序号缺口、重复包、乱序包、ACK 延迟、队列深度和重试次数。

采样设备至少包含一台 4GB RAM Windows 10/11 机器；记录 CPU 型号、GPU、驱动、分辨率、电源模式、DSH 版本和模型哈希，保证数据可复现。

## 3. 资源预算（初始工程门槛）

以下是**待验证的预算目标**，不是现有版本的测量值：

| 指标 | 目标 | 说明 |
|---|---:|---|
| 插件稳定态 Working Set | 100–180MB | 不包含 DSH 主进程和 Agent 进程 |
| 插件峰值 Working Set | ≤250MB | 模型加载、切换及短时资源解码期间 |
| Renderer JS heap 稳态 | ≤80MB | 以实际 Chromium/Electron 采样为准 |
| 纹理驻留预算 | 默认 1024 档，尽量 ≤32MB | 按实际模型、格式、mipmap 和 GPU 分配核算 |
| 帧时间 | 前台交互 P95 ≤16.67ms | 60Hz 目标；P99 单独报告，不隐藏尖峰 |
| Agent 消息 | 0 静默丢失 | 以端到端序号/ACK 对账验证 |
| 30 分钟稳态 | 无持续增长 | 允许缓存预热后进入平台期 |

若目标模型本身必须使用高分辨率贴图或大量遮罩，应显示“模型超出低配预算”的诊断，而不是隐式降低画质到不可接受或谎报满足预算。

## 4. 总体架构原则

### 4.1 单一 Runtime 所有权

以下状态只能由 Renderer 主线程中的唯一 Avatar Runtime 持有和修改：

- Cubism Model / Core 实例；
- Motion、Expression、Physics 更新顺序；
- ParamMixer 最终仲裁与 ParamInjector 写入；
- WebGL Context、纹理、遮罩和绘制状态。

Worker 不得直接修改 Cubism Model、Physics、Motion、Expression、ParamInjector 或 GPU Context。Worker 只处理可复制、可转移或不可变的数据，例如音频特征、轨迹采样、资源元数据和纯函数计算结果。

### 4.2 分层降级，不牺牲正确性

性能不足时按顺序降低非关键视觉成本：减少重绘频率 → 降低 render scale / 纹理档位 → 减少非必要特效 → 暂停隐藏视图绘制。不得通过丢弃 Agent 包、跳过参数所有权检查、并发写 Cubism 参数或省略动作回执来优化。

## 5. 分阶段实施

## P0：建立可观测性与性能基准

**目的：先知道时间和内存花在哪里。**

实现：
- 新增轻量 FrameProfiler，统计帧间隔、帧耗时、丢帧、P50/P95/P99；默认关闭高频明细，只保留低开销聚合。
- 新增 MemorySnapshot 适配层；能读取的字段按运行环境能力分级，不支持的字段标记 unavailable，不伪造 GPU 显存数据。
- 为 Agent 通道增加 queue depth、sequence gap、ACK latency、retry、duplicate、out-of-order 计数。
- 诊断信息可导出为 JSON，默认不包含聊天正文、文件路径、密钥或其他工作区敏感数据。

验收：
- 性能采样关闭时开销可忽略；开启时采样开销单独测量。
- 指标能区分 Renderer、插件 Host 和 Agent 进程。
- 每个指标标注来源、采样时间和可用性。

## P1：渲染调度与按需绘制

**目的：减少不必要的 GPU 提交，同时让活跃交互争取 60Hz。**

目标调度策略（初始建议，可根据实测调整）：

| 场景 | 目标刷新 |
|---|---:|
| 前台可见、拖拽/动作/交互中 | 最高 60Hz，受显示器刷新率与设备能力限制 |
| 前台可见、普通待机 | 30Hz |
| 长时间无交互且动作允许降速 | 15Hz，保留呼吸/眨眼的时间连续性 |
| 视图不可见 / 页面隐藏 | 暂停绘制；状态时钟按真实时间恢复 |
| 窗口恢复 | 立即同步时间并补绘，不突发补跑历史帧 |

实现要点：
- 统一 RenderScheduler，避免多套 RAF、定时器互相唤醒。
- 用单调时钟计算 deltaTime；降帧期间不通过连续补帧追赶历史时间。
- ActivityTracker 接收拖拽、动作、表情、注视、Agent 状态等活动信号；活动结束后设置滞回，避免刷新率频繁抖动。
- 用户主动交互期间临时升到 60Hz；结束后平滑回落。
- 尊重 prefers-reduced-motion / 用户性能档位。
- 隐藏时停止 GPU 绘制，但不能停止 Agent 消息消费、ACK、持久化和动作状态对账。

验收：
- 可见交互时测量 60Hz 能力；不能达到时报告实际帧率和瓶颈。
- 普通待机降到 30Hz，长待机可降至 15Hz。
- 隐藏 5 分钟绘制帧数不增长；Agent 数据仍正常收发。
- 恢复后不出现大 delta 导致的动作瞬移、物理爆振或参数跳变。

## P2：纹理、遮罩与 GPU 资源预算

**目的：压低显存/共享 GPU 内存和模型加载峰值。**

实现：
- 为模型资源增加纹理清单和预算计算，按真实宽高、像素格式、mipmap、重复引用计算估算值。
- 提供 2048 / 1024 / 512 纹理档位；默认低配档优先 1024，但必须保留原始资源且允许用户选择高质量档。
- 纹理降档应在加载前离线生成或缓存，不在每帧重采样。
- 按 drawable/mask 实际需求分配 mask RenderTexture；复用池并设上限，避免固定过量分配。
- 模型切换时明确销毁旧纹理、RenderTexture、监听器和临时 Blob URL。
- 处理 WebGL context lost/restored；恢复时重建资源，不保留失效句柄。
- 对纹理压缩格式做能力检测；不支持时使用安全回退。

估算参考：RGBA8 2048² 单张理论像素数据约 16MiB，1024² 约 4MiB；实际 GPU 占用还受 mipmap、对齐、驱动分配和 RenderTexture 影响，必须实测。

验收：
- 生成资源报告，记录原始/目标尺寸与估算预算。
- 同一模型在 1024 档的视觉质量由维护者验收。
- 连续切换模型 20 次后，GPU/内存资源无持续单调增长。
- context lost 后能恢复渲染，Agent 消息通道不受影响。

## P3：主线程减负与 Worker

**目的：把真正可并行的 CPU 工作移出渲染关键路径，而不是盲目增加线程。**

优先顺序：
1. 音频 RMS / FFT 特征提取（若当前版本启用音频输入）。
2. 轨迹预采样、动作链纯函数校验。
3. 大型资源元数据解析、缩略图/纹理预处理。
4. 经基准证明有收益后，再评估 ParamMixer 计算迁移。

协议要求：
- 消息必须包含 `sequence`、`requestId`、`generation`、`type`、`timestamp` 和版本化 payload。
- 大数组优先使用 Transferable ArrayBuffer，避免重复结构化克隆。
- Worker 只返回不可变结果；主线程校验 generation、参数白名单、所有权与时效后再应用。
- 队列有界；达到高水位时对可合并的连续状态帧做 latest-value coalescing，但不能合并/丢弃离散动作、ACK、错误、取消和状态变更事件。
- Worker 崩溃可重建；未确认的关键任务保留在主线程可靠队列中重放。
- 单 Worker 起步；只有压测证明并行收益超过调度/内存成本才增加 Worker 数量。

Agent 消息可靠性：
- 区分可合并状态快照与不可丢事件。状态快照可按 workspace + entity 合并到最新值；动作请求、动作回执、错误和控制事件必须逐条保留。
- 关键事件使用单调 sequence + ACK；超时重试必须幂等，接收端去重。
- 进程重启需要恢复未确认事件；若宿主不支持持久化，必须明确降级语义，不能声称 exactly-once。
- 队列满时执行背压并上报，不静默 drop；必要时暂停低优先级状态快照而非动作事件。
- 维护 workspaceId / sessionId 边界，拒绝跨工作区误投递。

验收：
- 10,000 条混合消息压力测试，关键事件端到端对账 100%。
- 覆盖重复、乱序、超时、队列满、Worker 崩溃、Renderer 暂停/恢复和宿主重启。
- 证明渲染主线程 P95 Long Task 降低；若没有收益，不合并 Worker 化改动。

## P4：启动、生命周期与打包轻量化

实现：
- 插件注册与 UI 可用优先；Cubism/Pixi/模型资源按需动态加载。
- 用户未打开角色视图时，不创建 WebGL Context、不加载模型纹理。
- 关闭视图后释放临时资源；若保留 Runtime，必须有明确的内存上限和闲置回收策略。
- 避免重复加载 SDK、重复 Runtime 和重复事件监听器。
- 检查生产 bundle，拆分仅调试使用的 profiler、诊断面板和测试工具。
- 评估依赖体积和重复依赖，不以压缩包体积代替运行时内存测量。

验收：
- 冷启动不等待模型加载。
- 未打开角色视图时无模型纹理驻留、无持续渲染循环。
- 打开/关闭角色视图 20 次无重复 Runtime 和监听器泄漏。

## P5：可选后端实验（不作为默认路径）

- OffscreenCanvas：先验证当前 Electron/Chromium、Cubism Core、Pixi 与 DOM 依赖。若 Cubism Core 必须依赖 DOM，保持 WebGL 主线程方案，不做强迁移。
- WebGPU：保留 WebGL 为稳定默认后端。只有在相同模型、相同效果、相同设备上的对照测试证明更低帧时间/内存后，才开放实验开关。
- 不将 WebGPU 或多线程作为低配优化的先决条件；线程和 API 更先进不等于实际更省资源。

## 6. 测试矩阵与验收门槛

### 6.1 场景矩阵

| 场景 | 时长 / 次数 | 观察项 |
|---|---:|---|
| 冷启动、首次打开角色 | 10 次 | 首帧耗时、峰值内存 |
| 前台连续交互 | 10 分钟 | FPS、帧时间分位数、Long Task |
| 普通待机 | 10 分钟 | 30Hz 策略、CPU/GPU 占用 |
| 隐藏/恢复 | 隐藏 5 分钟，重复 10 次 | 零绘制、状态恢复、消息完整 |
| Agent 消息压力 | 10,000 条 | 关键事件丢失、重复、乱序、ACK |
| Worker 故障注入 | 100 次 | 重建、重放、幂等 |
| 模型切换 | 20 次 | RAM/GPU 资源是否持续增长 |
| 4GB 内存压力 | 30 分钟 | 工作集、分页、卡顿、崩溃 |

### 6.2 发布门槛

- 功能正确性和参数所有权测试全部通过。
- Agent 关键事件丢失数为 0；重复事件必须可检测并幂等处理。
- 前台交互在目标测试机上报告真实 FPS 与 P95/P99；若 P95 超过 16.67ms，标记未达到 60Hz 目标并附瓶颈数据。
- 4GB 测试机 30 分钟运行无崩溃、无持续内存增长；记录是否发生系统分页压力。
- 隐藏状态不绘制，但通信和动作回执继续工作。
- 所有降级模式均可恢复，且不破坏动作链、参数所有权、工作区隔离和隐私边界。

## 7. 实施顺序与交付拆分

| 阶段 | 交付 | 前置条件 |
|---|---|---|
| S0 | 基准采集、Profiler、资源报告 | 先审计当前 main |
| S1 | RenderScheduler、ActivityTracker、隐藏暂停回归 | S0 |
| S2 | 纹理档位、Mask Pool、资源释放 | S0 |
| S3 | Agent 队列/ACK/去重/背压测试与可靠性修复 | 先盘点现有协议 |
| S4 | Worker 协议与首个高收益任务迁移 | S0、S3 |
| S5 | 按需加载、bundle 与生命周期瘦身 | S0–S2 |
| S6 | OffscreenCanvas/WebGPU 对照实验 | 前述阶段稳定后 |

建议拆分成多个实现 PR：先提交 S0 基准与观测，再逐步合入渲染、资源、通信和 Worker 改动。避免把调度器、纹理管线、消息协议和渲染后端一次性大改，导致性能回归难以定位。

## 8. 代码审计入口

实现前需以最新 main 重新核对以下模块及其调用关系（路径仅作审计入口，若已移动以当前目录为准）：

- Renderer RAF / tick / 生命周期：`packages/renderer/src/app/lappdelegate.ts`、`lappsubdelegate.ts`
- Cubism 模型、纹理与遮罩：`packages/renderer/src/app/lappmodel.ts`
- 参数仲裁与注入：`packages/core/src/mixer.ts`、`packages/renderer/src/app/param-injector.ts`
- 参数所有权：`packages/renderer/src/app/param-ownership.ts`
- 动作冲突与收尾：`packages/renderer/src/app/motion-director.ts`
- Workspace Agent 消息桥：`packages/dsh-l2d-plugin/lib/workspace-agent.mjs`
- 测试入口：根目录 `package.json` 中的 `test:core`、`test:types`、`accept`、`test:contract`，以及 renderer build/test。

重点核实已有 60Hz、动态 renderScale、隐藏暂停、纹理降档、mask pool、消息 ACK 等是否已经存在，避免重复实现或覆盖近期修复。

## 9. 风险与明确不做的事

- 不承诺仅凭“4GB RAM”即可让任意 Live2D 模型稳定 60Hz。
- 不把 30/15Hz 待机策略应用到用户正在拖拽或动作执行的交互阶段。
- 不在 Worker 内写 Cubism 参数或持有共享可变 Runtime。
- 不为提升 FPS 丢弃动作事件、回执或 Agent 工作区上下文。
- 不默认启用 WebGPU/OffscreenCanvas。
- 不以单次 FPS 截图代替长时间压力测试。
- 不把纹理预算估算、JS heap、Working Set 和 GPU 显存混为同一指标。

## 10. Reviewer Checklist

- [ ] 所有基线指标都有设备、版本、模型和采样方法。
- [ ] 60Hz 是实测目标而非未经验证的保证。
- [ ] 渲染降频不会暂停 Agent 通道。
- [ ] Worker 不会绕过 ParamOwnership / ParamInjector。
- [ ] 关键消息有序号、ACK、幂等去重、背压和恢复策略。

- [ ] 所有性能改动有对照数据和回归测试。
