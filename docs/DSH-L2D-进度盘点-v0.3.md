## 一、先对齐基线：需求变了

你在上一轮补充的四条，把产品形态从「独立桌面 App」改成了「DSH 内的插件 + 悬浮层」。这不是细节调整，是形态变更，必须先确认再往下做。

| # | 新需求 | 对架构的影响 |
|---|---|---|
| 1 | 直接连 DeepSeekHarness，与其它插件联动 | 需要 DSH 插件适配层；本项目不再是独立应用，而是宿主的一个扩展 |
| 2 | 像 DSH QQbot 那样，开一个**会话**专门管理动作 | 动作控制要学会话化：用户用自然语言说「让她挥个手」，由带工具的 Agent 会话执行 |
| 3 | 对话窗口能从**其它工作区**读取 | 需要跨工作区上下文通道；角色侧只需订阅消息事件来驱动听说状态 |
| 4 | 角色以**透明底色悬浮窗**浮在 DSH 主页面上 | 渲染层要能被悬浮窗加载，且窗口透明、无边框、可点击穿透 |

**结论**：原先「Electron 独立壳 + 自有舞台页」的重心要后移，优先级变成 **DSH 插件集成 > 悬浮窗 > 渲染内核**。前两项我目前**没有 DSH 的任何接口资料**，是硬阻塞（见第五节）。

## 三、已做（可验证，不是纸面）

### 3.1 模型格式适配 —— 这条最有价值，且已验证

`tools/vts-adapter/index.mjs`（Node，零依赖）。解决的是：你这份 DeepSeek 公皮是 **VTube Studio 包**，`model3.json` 里 Motions/Expressions 全空，任何非 VTS 渲染器加载都会「能显示但无表情无动作」。

实测输出：

```
热键总数 28 → 表情 21 + 动作组 7
参数映射校验：0 / 40 条无效
Groups 修复：LipSync 组为空 → 注入 ParamMouthOpenY
纹理预算：592 MB 显存（含 8192×8192）
```

**为什么这条对新需求同样有用**：产出的 `capabilities.json` 正是「动作管理会话」里工具定义的数据源。会话要能让大模型知道「这个角色有哪些表情、哪些动作组」，就是读这个文件。所以不算为旧形态白做。

### 3.2 参数仲裁器 ParamMixer

`packages/core/src/mixer.ts`，约 230 行，7 项冒烟测试全通过（`pnpm test:core`）。

| 能力 | 实现情况 |
|---|---|
| 分层求值（六层通道，按优先级升序） | 完成 |
| `override` / `add` 双混合模式 | 完成 |
| 动作锁（hardLock，高优先级占用后低优先级跳过） | 完成 |

| 按参数类别区分平滑时间常数（眼 30 / 头 120 / 身 300 / 呼吸 900 ms） | 完成 |

## 七、两条待选路线

### 路线 A：DSH 托管（推荐，前提是宿主支持）

```
DSH 主窗口
 ├─ 插件进程（DSH-L2D）
 │   ├─ 动作管理会话 ← 工具集来自 capabilities.json
 │   ├─ 事件适配：订阅会话/工作区消息 → 驱动听说状态
 │   └─ 本地 WebSocket 服务（127.0.0.1）
 └─ 悬浮层（透明）
     └─ Live2D 渲染入口 ← 连本地 WS，只负责画
```

优点：形态最贴合你的描述；打包最轻；无需 Electron。风险：完全依赖宿主能力。

### 路线 B：插件 + 自带 Electron 浮层

插件负责会话与逻辑，Electron 只承担「透明置顶窗 + 点击穿透」这一个职责。

优点：宿主能力不足时仍能实现悬浮效果；跨平台可控。
风险：多一层进程与打包开销；与宿主窗口的层级关系需要调试（尤其全屏应用时）。

**选择依据**：DSH 插件能否创建窗口 / 能否渲染透明层的答案。
