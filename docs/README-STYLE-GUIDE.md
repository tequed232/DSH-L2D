# README 编写与视觉规范

> 本文是 DSH-L2D 根目录 README 及相关项目介绍文档的长期维护规范。后续 Agent 修改 README、项目首页或介绍性文档时，必须先阅读本文，并以仓库当前代码为事实来源。

## 1. 目标与设计方向

README 应当像一个成熟开源项目的产品首页，而不是随手堆叠的功能清单或内部开发日志。

参考视觉方向：
- 顶部具有明确的品牌识别：项目图标、项目名称、一句话定位。
- 使用居中 Hero 区域，控制宽度与信息密度。
- 使用少量高质量 Shields badges 展示平台、渲染技术和许可证。
- 使用简洁的锚点导航，让读者快速进入功能、架构、安装和开发章节。
- 正文采用分层标题、卡片式功能区、表格、代码块和架构图组合。
- 用 Emoji 作为章节视觉锚点，但不要每一行都加 Emoji。
- 保持深色/浅色 GitHub 页面均可读；不依赖固定背景色或自定义 CSS。
- 长文档要有清晰目录、足够留白和可扫描的信息层级。

## 2. 推荐页面结构

根 README 默认按以下顺序组织；确实不适用的章节可以省略，但不能为了凑结构制造空内容。

1. **Hero**：项目 Logo、项目名称、Slogan、定位、2–4 个 badges、锚点导航。
2. **项目简介**：解决什么问题、面向谁、与普通 Viewer/参数脚本的区别。
3. **功能一览**：使用 HTML table 构建两列功能卡片，每卡片 3–5 个简短能力点。
4. **实现状态**：区分已实现、部分实现、实验性、规划中；不能把设计目标写成已交付。
5. **运行架构**：优先使用 Mermaid flowchart 展示真实数据流，并用表格解释 package 职责。
6. **核心机制**：解释语义意图、能力画像、轨迹、仲裁和参数写入。
7. **宿主 / Agent / MCP 集成**：描述真实 Host API 与调用边界，明确哪些路径已经接线。
8. **快速开始**：提供从干净环境可执行的步骤；环境、安装、构建、部署和模型资源配置分开。
9. **开发与验证**：命令必须来自 package.json 或实际脚本；区分单元测试、构建、集成验收和真机验收。
10. **目录结构、路线图、设计文档、安全/许可和贡献说明**。

## 3. 视觉与 Markdown 规则

### 3.1 Hero 区域

推荐形式：

~~~html
<div align="center">

<img src="相对路径/项目图标.png" width="144" alt="项目名称" />

# PROJECT-NAME

### 一句话 Slogan

项目中文定位说明。

<p>
  <img src="Shields badge URL" alt="Badge" />
</p>

<a href="#功能">功能</a> · <a href="#架构">架构</a> · <a href="#快速开始">快速开始</a>

</div>
~~~

要求：
- 优先使用仓库内真实存在的 Logo，不得虚构图片路径。
- Badges 建议 2–4 个，统一使用 Shields.io 的 `style=for-the-badge` 或 `flat-square`。
- Badge 只展示稳定事实，如平台、主要技术、许可证；不要用 Badge 宣称未经验证的测试通过率、性能或完成度。
- 不要堆叠大量动态徽章、无关社交链接或装饰图片。

### 3.2 功能卡片

GitHub README 可使用 HTML table 做稳定的两列布局：

~~~html
<table>
<tr>
<td width="50%" valign="top">

### 功能类别
- 能力一
- 能力二
- 能力三

</td>
<td width="50%" valign="top">

### 另一类别
- 能力一
- 能力二
- 能力三

</td>
</tr>
</table>
~~~

- 每张卡片聚焦一个主题。
- 单卡片建议 3–5 个条目。
- 不要将未实现的路线图项目混入当前功能卡片。

### 3.3 架构图

- 优先 Mermaid，确保节点描述简短，方向明确。
- 图必须反映真实调用链，不允许把理想架构伪装成当前实现。
- 设计目标与现有代码不一致时，标注“目标架构”。
- 复杂架构图下方必须用表格解释 package 职责。

### 3.4 表格与代码块

- 表格列数尽量控制在 2–4 列。
- 单元格内容简短，长解释放到表格外。
- 命令必须使用 fenced code block，并标明语言。
- 路径、环境变量、命令、API 名称使用反引号。
- 代码示例必须与当前实现一致；示意代码要明确标记为伪代码或示例。

### 3.5 Emoji 与标题

- 一级标题只用于项目名称或页面主标题。
- 二级标题用于主要章节，三级标题用于章节内部主题。
- 每个主要章节可使用一个有语义的 Emoji。
- 不使用 Emoji 替代技术名词或状态标记。

## 4. 内容准确性规则（强制）

### 4.1 事实来源优先级

按以下顺序核对：

1. 当前分支实际源码。
2. 当前 package manifests、配置和脚本。
3. 自动化测试、验收工具和真实运行记录。
4. 最新架构审计与接口文档。
5. 历史设计文档和讨论记录。

如果文档与代码冲突，以代码为准，并在必要时修正文档或指出不一致。

### 4.2 状态标签必须区分

建议使用以下措辞：

- **已实现**：源码存在，且核心路径有测试或可复现证据。
- **部分实现**：有模块或局部接线，但端到端链路尚未完成。
- **实验性**：接口或行为仍可能变化，缺少稳定性保证。
- **规划中**：仅存在设计、Issue 或 TODO，尚无可用实现。
- **已验证**：必须给出验证环境、命令或测试证据。
- **未验证**：不能暗示真实宿主、模型或 GPU 已经通过验收。

禁止：
- 将类型定义等同于功能完成。
- 将 README/设计文档中的目标等同于运行时代码。
- 将 mock、stub、测试夹具描述成生产能力。
- 将某个 Host slot 可用推断为所有容器均可用。
- 将 MCP 请求 accepted 描述成动作已经完成。
- 将“支持 GPU/多核”写成事实，除非代码路径和基准数据能证明。

### 4.3 命令与安装步骤

每次修改安装说明前：
1. 读取根目录 `package.json`、workspace 配置和相关 package manifest。
2. 检查脚本实际指向的文件。
3. 确认命令参数、输出目录和环境变量。
4. 若涉及 DSH 安装，核对当前 Host 版本的安装机制。
5. 不确定的步骤应写成“请按当前宿主版本确认”，不能编造 profile 路径。

### 4.4 图片和资源

- 只引用仓库中存在的图片或可长期访问的官方资源。
- 不得创建虚构截图、演示 GIF、下载链接或文件路径。
- 模型与 Cubism Core 受独立许可约束，README 不得暗示可随仓库自由分发。
- 如果尚无真实演示图，应保留简洁 Hero，不要用无关素材填空。

## 5. DSH-L2D 特定架构术语

后续 Agent 应统一使用以下概念：

| 术语 | 定义 |
|---|---|
| Host | DSH 插件宿主，管理插件生命周期、服务和宿主扩展点 |
| Renderer | Cubism / WebGL 运行时，负责模型和画面 |
| Core | 模型无关的语义动作、轨迹和参数仲裁逻辑 |
| Avatar Runtime | 角色的唯一权威行为与模型运行时状态 |
| Presentation | 角色显示在哪个容器，不拥有动作状态 |
| Capability Profile | 当前模型实际可用的身体/动作能力画像 |
| Semantic Intent | Agent 表达的行为目标，不是底层逐帧参数 |
| WriteIntent | 经过约束的参数写入意图 |
| Ownership | 某个动作/通道对参数的独占或仲裁关系 |
| MCP Bridge | MCP Server 到插件本机 HTTP 接口的调用桥 |

必须坚持：
- 单一权威 Avatar Runtime。
- 行为状态与 Presentation 容器分离。
- Agent 产生语义意图，本地运行时确定性执行。
- 未知模型能力不推断为支持。
- 所有参数写入都经过统一仲裁和合法的 Cubism 更新阶段。
- 宿主没有公开的 API 或事件，不得在 README 中假设其存在。

## 6. 后续 Agent 修改 README 的工作流程

每次修改必须按顺序执行：

1. **读取本规范**：先阅读 `docs/README-STYLE-GUIDE.md`。
2. **读取现有 README**：理解当前内容和锚点链接，避免无意删除仍有效的安装说明。
3. **检查代码事实**：至少检查根 `package.json`、workspace 配置、相关 package manifest、核心入口、测试和实际使用到的 API。
4. **建立事实清单**：列出每个能力对应的源码路径和验证证据；无法确认的内容标记为未验证。
5. **先定信息架构**：确定 Hero、功能、架构、安装、开发、路线图章节，再撰写内容。
6. **检查链接**：所有相对路径必须在当前分支存在；外部链接必须指向官方或稳定页面。
7. **检查渲染**：检查 Markdown/HTML/Mermaid 是否符合 GitHub README 支持范围；避免自定义 CSS、脚本和不支持的组件。
8. **检查差异**：确保 README 不误删资源授权、隐私、安全和安装限制。
9. **验证与报告**：文档变更可不跑运行时测试，但必须说明未运行；若安装命令或代码接口变化，应执行对应验证。
10. **提交 PR**：说明依据、变更章节、未验证项和需要维护者确认的问题。

## 7. Review Checklist

提交前逐项确认：

- [ ] Hero 图片路径真实存在，项目定位准确。
- [ ] Badges 数量适当，内容没有未经证实的宣传。
- [ ] 目录锚点和相对链接有效。
- [ ] 功能区只描述当前代码已经具备的能力。
- [ ] 架构图区分当前实现与目标架构。
- [ ] Core / Renderer / Host / MCP 职责没有混淆。
- [ ] 安装和构建命令已从脚本核实。
- [ ] 模型、Cubism Core 的授权边界清晰。
- [ ] 本机 HTTP、API Key、传感器和工作区上下文的安全边界保留。
- [ ] 测试、集成验收和真机验证没有混为一谈。
- [ ] 未使用不存在的截图、文件、API、命令或环境变量。
- [ ] README 在 GitHub 深色与浅色主题下都易读。

## 8. 修改原则

README 是项目入口，不是所有技术细节的唯一存放位置。

- 项目定位、快速开始和模块概览写在 README。
- 深入接口、状态机、参数时序和设计决策写在对应 docs。
- 具体实现细节应通过链接指向源码或专题文档。
- README 应保持可扫描，不复制整篇设计文档。
- 每次改动以事实准确、易读和可维护为优先，不以篇幅或装饰数量作为质量指标。


## 9. 产品展示与媒体规范

README 的视觉方向可以更接近轻量产品官网，但仍须保留 GitHub 文档的可访问性、可维护性和事实准确性。产品化不等于堆叠装饰或营销文案。

### 9.1 产品官网式信息呈现

- Hero 应突出项目识别、核心价值和主要入口；避免过长的首屏文字。
- 功能展示优先采用主题明确的卡片或双栏布局，每张卡片只表达一个价值点。
- 重要能力可以配合真实运行截图、局部 UI 截图或短 GIF，形成“能力说明 + 实际画面 + 简短解释”的展示单元。
- 视觉风格应与 DSH-L2D 的蓝色、Live2D 和鲸鱼女仆角色主题一致，但不能牺牲文字对比度和信息层级。
- 不使用未经验证的性能数字、夸张承诺或将路线图功能包装成现有功能。
- README 在手机窄屏下必须仍然可读；避免过宽表格、横向大图和过多并排卡片。

### 9.2 项目主视觉与角色图

- 项目维护者提供并确认的角色图可以作为项目主视觉；优先使用仓库内版本化资源。
- 主视觉的原图应保留，不要为了 README 强行覆盖或破坏原始文件；如需圆形图标、缩略图或透明底版本，应另存衍生资源。
- 图片路径必须在当前分支真实存在，大小写与扩展名必须完全匹配。
- 图片应提供准确的 alt 文本；装饰性图片可使用简短描述，不应把整段宣传文案写入 alt。
- 后续 Agent 不得擅自用网络搜索到的相似角色图替换维护者确认的主视觉。
- 未完成图片上传时，不得先在 README 中引用一个尚不存在的资源路径。

### 9.3 Live2D 运行截图与动作 GIF

- 优先使用真实 DSH 环境和真实 Live2D 模型录制的截图或 GIF。
- 截图应展示实际 UI、角色状态或功能操作，不得用静态插画冒充运行效果。
- 动作 GIF 应短小、循环自然、重点明确；建议每个 GIF 只演示一个行为，例如待机、视线跟随、情绪动作链或容器切换。
- GIF 应控制文件大小和尺寸；过大的素材优先转为外链视频，不要让 README 首屏加载大量媒体。
- 录制前清理账号标识、工作区私密信息、文件路径、API Key、会话内容和其他敏感信息。
- 对实验性功能，图片旁必须标注实验状态或演示环境，不能暗示为稳定发布能力。
- 没有真实素材时，保留文字说明或明确的待补素材清单，不得生成虚构截图、GIF 或占位图片冒充成品。

### 9.4 Bilibili 视频嵌入规范（后续补充）

GitHub README 不支持可靠地直接运行 Bilibili 的 iframe/embed 播放器。后续获得正式视频链接后，默认使用“封面卡片 + 点击跳转 Bilibili”的兼容方案，而不是把 iframe HTML 写进 README。

推荐结构：

~~~markdown
## 🎬 演示视频

<div align="center">

<a href="https://www.bilibili.com/video/BVxxxxxxxxxx/">
  <img src="真实可访问的视频封面地址" alt="DSH-L2D 功能演示视频封面" width="720" />
</a>

**点击封面，在 Bilibili 观看完整演示**

</div>
~~~

执行要求：
- 在维护者提供真实 BV 号或完整链接之前，不添加虚构 BV 号、视频封面 URL 或伪造播放按钮。
- 后续收到链接后，先确认视频确实对应 DSH-L2D，再选择官方封面或仓库内自制封面。
- 封面图片必须可长期访问；优先使用仓库内压缩后的封面资源，或经过确认的 Bilibili 官方封面地址。
- 链接应直接指向视频页面；如有明确的分 P，保留正确的分 P 参数。
- 在链接旁说明视频内容，例如“插件安装与初始化”“Live2D 待机和动作链”“Agent 工作区事件联动”。
- 不依赖 GitHub 对 iframe、script、object 或自定义 HTML 播放器的支持。
- README 仍应保留文字版功能说明，视频不能成为理解项目的唯一入口。

在没有视频链接时，**只保留本规范，不在 README 中展示空视频区块**。等维护者提供 BV 链接后，再增加正式的视频卡片。

### 9.5 快速安装说明的版本适配

安装文档必须面向明确的 DSH 版本或版本范围，不能只写一套未经确认的通用步骤。

每次调整安装说明时：
1. 核对目标 DSH 版本、插件 API 版本和最低运行环境。
2. 从当前 DSH 版本源码或官方文档确认插件发现、安装、启用、配置和重启流程。
3. 核对插件 package 的实际构建产物、入口文件、资源目录和依赖声明。
4. 分开说明开发者本地构建安装与普通用户安装；不要混用 `pnpm dev`、`npm pack` 和宿主安装步骤。
5. 对需要手动复制的文件，列出准确源路径和目标路径；无法确认的目标路径不得猜测。
6. 对模型文件、Cubism Core 和用户配置说明各自的放置方式、许可边界和安全注意事项。
7. 如果不同 DSH 版本的安装流程不一致，使用版本分支说明或兼容性表，不要把某一版本的步骤写成普遍规则。
8. 安装后提供最小验证步骤：插件是否被宿主发现、服务是否启动、客户端入口是否注入、Renderer 是否能按需加载。
9. 标明已验证的 DSH 版本、操作系统和验证日期；未实测的组合明确标注“未验证”。

## 10. 媒体与产品化 Review Checklist

后续涉及 README 视觉升级时，除第 7 节原有清单外，还应确认：

- [ ] Hero 使用维护者确认的项目主视觉，且资源路径真实存在。
- [ ] 产品展示卡片对应真实能力，不把路线图内容写成现有功能。
- [ ] Live2D 截图和 GIF 来自真实运行环境，且已清理敏感信息。
- [ ] GIF 数量、尺寸和文件大小合理，不影响 README 加载。
- [ ] Bilibili 链接未提供时，只保留本规范，不出现空播放器或虚构视频卡片。
- [ ] 后续添加 Bilibili 视频时使用封面链接跳转，不依赖 iframe 播放。
- [ ] 视频封面真实可访问，视频内容与描述一致。
- [ ] 快速安装步骤针对明确 DSH 版本核对，开发安装和用户安装没有混淆。
- [ ] README 在移动端、GitHub 深色和浅色主题下均可读。
