# DSH-L2D 行为与情境系统设计 v0.1

> 目标：让角色在 **待机 / 用户问答 / 用户操作电脑** 三种情境下表现出不同且合理的行为，而不是「不说话的模型」或「一直傻笑的模型」。
> 前置：`DSH-L2D-技术栈方案-v0.2.md`、`DSH-L2D-技术方案-v0.1.md` §4.1（ParamMixer）。
> 日期：2026-11-01。

---

## 0. 一句话结论

这不是「三套动画」，而是**一个情境感知层 + 一个行为调度状态机 + 一个参数仲裁器**的三级结构。做成三套 if-else 动画必然崩，因为真实场景里状态是连续漂移、会互相打断、会有中间态。

---

## 1. 情境定义（不是按时间划分，而是按信号判定）

四个状态，其中三个是你要求的，第四个是必须补的——否则电脑锁屏/离开时角色会一直空转耗电。

| 状态 | 判定信号（全部满足） | 典型场景 |
|---|---|---|
| **IDLE 待机** | 无语音活动 ∧ 无键鼠输入 ∧ 无对话进行中（持续 ≥ 8s） | 用户在看视频、发呆、离开座位 |
| **CONVERSATION 问答** | VAD 检测到用户在说话 ∨ TTS 正在播放 ∨ LLM 正在生成 ∨ 上一轮结束后 3s 内 | 一问一答、连续对话 |
| **WORK 用户操作** | 键鼠输入活跃（最近 5s 内有事件）∧ 不处于 CONVERSATION | 写代码、打字、切窗口、打游戏 |
| **AWAY 离席** | 系统空闲 ≥ 5min（Windows `GetLastInputInfo` / Electron `powerMonitor.getSystemIdleTime()`） | 锁屏、离开、午休 |

**判定要点**：

- **状态是带滞回的**。进入 WORK 只需「有输入」，退出 WORK 要「静默 8s」，否则打字间隙会疯狂闪烁切换。
- **CONVERSATION 优先级最高**，可直接打断 WORK 与 IDLE。
- **AWAY 优先级最低但不可被误触发**，必须用系统级空闲时长，不能用「我们自己的定时器」。

---

## 2. 架构位置

```
┌─────────────────────────────────────────────────────────────┐
│  L2.5  情境层 ContextEngine                                  │
│        信号聚合 → 状态判定（带滞回）→ 输出 Context + 置信度    │
├─────────────────────────────────────────────────────────────┤
│  L2.6  行为层 BehaviorDirector                               │
│        行为库 · 状态机 · 打断规则 · 情绪惯性(mood) · 节流      │
│        输出「意图」：{expression, motion, gaze, paramHint}    │
├─────────────────────────────────────────────────────────────┤
│  L3    混合层 ParamMixer（v0.1 §4.1）                        │
│        把行为意图 + 面捕 + 口型 + 物理基座合成最终参数         │
└─────────────────────────────────────────────────────────────┘
```

**关键分层意义**：行为层**不直接写参数**，只输出「意图」。这样同一套行为可以在不同模型上降级执行（模型没有某个表情就跳过，而非报错）。

## 3. 状态机

```
                    ┌──────────── 用户在说话 / AI 在回应 ────────────┐
                    ▼                                              │
   ┌────────┐   8s 无活动   ┌──────────────┐   输入活跃 5s   ┌──────────┐
   │  AWAY  │◀─────────────│     IDLE     │───────────────▶│   WORK   │
   │ 离席   │  系统空闲5min │    待机      │◀───────────────│ 操作电脑 │
   └────────┘              └──────────────┘   静默 8s      └──────────┘
        ▲                         │  ▲                            │
        │                         │  └──── 对话结束 3s ───────────┘
        │                         ▼
        │                  ┌──────────────┐
        └──────────────────│ CONVERSATION │  （最高优先级，双向可中断）
                           │    问答      │
                           └──────────────┘
```

**四条迁移规则**：

1. `CONVERSATION` 可从任意状态进入，进入时**立即**衰减当前行为权重，用 200ms 交叉淡入。
2. `CONVERSATION → IDLE` 有 3 秒情绪残留期（笑完不会瞬间面无表情）。
3. `WORK → IDLE` 需静默 8s，防抖。
4. `AWAY` 只能由系统空闲触发，进入时**降到 10fps** 并停用物理高频求值。

## 4. 各状态的行为清单

以下全部对应实测模型（21 表情 / 7 动作组），可直接落地。

### 4.1 IDLE 待机 —— 目标：像一个「在等人」的活人

| 行为 | 实现 | 频率/参数 |
|---|---|---|
| 呼吸 | `ParamBreath` 正弦 | 周期 3.5s，幅度 0.5 |
| 自动眨眼 | `ParamEyeLOpen/ROpen` | 3～7s 随机，双眨概率 15% |
| 视线漂移 | `ParamEyeBallX/Y` | 每 2～4s 换一个随机目标点，带缓动 |
| 身体微摆 | `ParamBodyAngleX/Z` | 周期 8s，幅度 ±3 |
| 待机动作 | `Idle` 动作组循环 | 基础层 |
| 姿态小变化 | 随机切「前倾」「尾巴开关」等表情 | 每 40～90s 一次，权重低 |
| 被注视反应 | 鼠标靠近/悬停模型 → 视线转向光标 | 即时 |

**不要做的事**：待机时不要随机播「竖手指」「狗尾巴草」这类**状态切换动作**——它们成对存在且 `Loop:true`，随机播会卡在奇怪状态。这些必须由事件或对话触发，且用状态机管理开/关。

### 4.2 CONVERSATION 问答 —— 目标：说话有节奏、有情绪、不像朗读

按四个子阶段分别设计（这是体验好坏的关键，多数项目只做了「说话」一个阶段）：

| 子阶段 | 时长 | 表现 |
|---|---|---|
| **LISTENING 聆听** | 用户说话期间 | 视线锁定用户（或摄像头方向）、轻微前倾、眨眼频率略降、每 1.5s 一次微点头 |
| **THINKING 思考** | 从提交到首 token（300～1200ms） | **必须有**：歪头 + 视线右上 + 眉心上挑 + 偶尔「＞＜」；这是遮盖 LLM 延迟的核心手段 |
| **SPEAKING 说话** | TTS 播放期间 | 口型（RMS 硬覆盖）+ 每句一个表情 + 每 2～3 个重音一次点头（`beat` 驱动）+ 结尾语气收束动作 |
| **SETTLE 收尾** | 结束后 1～3s | 表情缓慢回落到中性或上一情绪，不硬切 |

**情绪映射**：LLM 输出的 `expression` 走枚举约束（见 v0.1 §4.2），但需要一张**语义 → 本模型表情**的词典：

| 语义 | 本模型可用表情 |
|---|---|
| joy / happy | 兔牙、脸红 |
| sad / cry | 流泪、流冷汗 |
| angry | 黑脸 |
| shy | 脸红、＞＜ |
| smug | 屑屑眼 |
| surprise / shock | 钢盆、圈圈眼 |
| love | 爱心眼 |
| thinking | 前倾 + ＞＜ |

词典外置为 `mapping/expression-semantic.json`，换模型只改词典，不改代码。

### 4.3 WORK 用户操作 —— 目标：像在旁边陪着，但不打扰

这是最容易被做烂的一环：做成「每个键盘事件都触发动作」会变成抽搐。正确做法是**先聚合，再反应**。

**信号聚合（关键）**：

```
原始事件（数百 Hz）  →  滑动窗口聚合  →  语义标量
─────────────────────────────────────────────────
按键事件             →  打字速率 (keys/5s) → 0~1 强度
鼠标位移             →  移动速度           → 0~1
鼠标点击             →  点击脉冲           → 事件
窗口切换             →  切换脉冲           → 事件
```

| 行为 | 触发条件 | 表现 |
|---|---|---|
| 视线跟随光标 | WORK 态持续 | `ParamEyeBallX/Y` 跟随鼠标，权重 0.7 |
| 转头看屏幕 | 光标靠近屏幕边缘/大幅移动 | `AngleX/Y` 小幅参与 |
| 打字节奏反应 | 打字速率 > 阈值 | 每隔 ~4s 一次极轻微的头部点动（幅度 ≤2°），**不是每次按键** |
| 高强度打字 | 打字速率持续 > 阈值 30s | 换「＞＜」或「流冷汗」表情，表达"好忙" |
| 窗口切换 | 切换脉冲 | 头部快速转向 + 眨眼，一次 |
| 长时间静止但未离席 | 3min 无输入 | 回落到 IDLE 的微动作 |
| 全屏应用/游戏 | 检测到全屏 ∧ 前台非本应用 | **静默降级**：降到 15fps、停用视线跟随、只保留呼吸 |

**全屏降级是必须做的**：用户打游戏时角色还在旁边高频转头，会被立刻卸载。

### 4.4 AWAY 离席 —— 目标：不烧电

- 降到 10fps，物理求值降频到 20Hz
- 可选：切「加载」或闭眼姿态，回来时有一次「醒来」的眨眼 + 抬头
- 恢复时不要突然全速，用 1s 淡入

## 5. 打断与优先级

| 优先级 | 行为类型 | 示例 |
|---|---|---|
| 100 | 用户直接交互 | 点击模型、拖拽 |
| 80 | 对话事件 | 开始说话、情绪切换 |
| 50 | 情境反应 | 窗口切换转头、高强度打字表情 |
| 20 | 待机微动作 | 视线漂移、姿态变化 |
| 10 | 物理/呼吸 | 基座 |

规则：

- 高优先级可**立即**打断低优先级，但被中断的行为要在结束后**平滑恢复**（不是回到原点，而是重新进入该状态的当前相位）。
- 同级行为**不抢占**，先到先执行，后到排队。
- 任何行为都要有 `enter / update / exit` 三个钩子，`exit` 里负责把参数交还给下层，防止参数被"锁死"。

## 6. 情绪惯性（mood）

没有这个变量，角色会显得"精神分裂"：上一秒笑、下一秒面无表情。

```
mood ∈ [-1, 1]（效价） 与 arousal ∈ [0,1]（唤醒度）
每次对话事件：mood += Δ（幅度小，0.1~0.2），并随时间回归 0（时间常数 ~60s）
待机时：mood 以极慢速度漂移，偶尔触发自言自语式微表情
```

mood 的作用：作为 IDLE 与 CONVERSATION 之间的**黏合剂**——对话结束后 mood 仍为正 → 待机保持微笑表情一段时间，而不是瞬间归零。

## 7. 工程实现要点

### 7.1 信号采集（Windows）

| 信号 | 方案 | 说明 |
|---|---|---|
| 系统空闲时长 | Electron `powerMonitor.getSystemIdleTime()` | **零成本**，优先用 |
| 全局键鼠 | `koffi` 调 `user32.dll` `GetAsyncKeyState` 轮询（20Hz） | 需原生依赖；仅统计"是否有输入 + 速率"，**不记录内容** |
| 前台窗口 | `GetForegroundWindow` + `GetWindowTextW` | 仅取进程名/是否全屏，**不读标题内容** |
| 全屏检测 | 前台窗口矩形 == 屏幕矩形 | 用于降级 |

Electron 的 `powerMonitor` 只能给"空闲了多久"，给不了"正在打字"，所以全局键鼠钩子是**必需的**，无法用纯 Electron API 替代。

### 7.2 信号采集（Android）

| 信号 | 方案 |
|---|---|
| 空闲 | `PowerManager.isInteractive` + 无触摸计时 |
| 前台应用 | `UsageStatsManager`（需 `PACKAGE_USAGE_STATS` 特殊权限，引导用户授权） |
| 键鼠 | 不适用，改为触摸频率 |

Android 侧能力显著弱于 Windows，建议 **WORK 态在 Android 上简化为「触摸活跃/静止」两档**，不做窗口级反应。

### 7.3 隐私红线（必须写进产品文档）

- 全局键鼠钩子**只产出聚合标量**（速率、有无），**不落盘、不上传、不记录按键内容**。
- 前台窗口只取**是否全屏**与**是否为本应用**，不读取窗口标题文本。
- 设置页提供一键关闭，关闭后行为回落到 IDLE。
- 这些是用户会追问的点，也是上架审核（尤其 Android）的必查项。

### 7.4 配置化

行为不写死在代码里，用 JSON 描述，便于调参与换角色：

```json
{
  "states": {
    "idle": {
      "fps": 60,
      "ambient": [
        { "type": "breath", "period": 3.5, "amp": 0.5 },
        { "type": "blink", "interval": [3, 7], "doubleChance": 0.15 },
        { "type": "gazeDrift", "interval": [2, 4] }
      ],
      "idleMotion": "Idle"
    },
    "work": {
      "reactions": [
        { "on": "typingRate", "above": 0.6, "for": 30000, "expression": "＞＜", "cooldown": 60000 },
        { "on": "windowSwitch", "motion": "lookAtScreen", "cooldown": 3000 }
      ],
      "degrade": { "onFullscreen": true, "fps": 15 }
    }
  }
}
```

## 8. 与 ParamMixer 的对接

行为层输出的是**意图**，由 ParamMixer 按 v0.1 §4.1 的规则合成：

| 行为意图 | 进入的通道 | 混合方式 |
|---|---|---|
| `expression: "脸红"` | 表情通道 | soft-add，权重 0.8 |
| `motion: "竖手指打开"` | 动作通道 | 独占锁，状态机管理 |
| `gaze: {x, y}` | 程序化通道 | 覆盖 `ParamEyeBallX/Y`，权重 0.7 |
| 口型 | 口型通道 | 硬覆盖，行为层**无权**写入 |
| 打字微点头 | 程序化通道 | add，幅度极小 |

**重要约束**：口型参数是行为层的**禁区**。行为层永远不能直接写 `ParamMouthOpenY`，否则会和 RMS 包络打架，产生典型"嘴抽搐"。

## 9. 验收标准

| 指标 | 目标 |
|---|---|
| 状态切换无跳变 | 任意切换有 ≥200ms 交叉淡化，无参数突变 |
| 待机 5 分钟观感 | 无重复感（同一动作不连续出现）、无静止期 > 6s |
| 打字时无抽搐 | 连续输入 60s，头部动作 ≤ 6 次 |
| 思考态覆盖率 | 首 token 等待期 100% 有思考表现 |
| 全屏降级生效 | 进入全屏 1s 内 fps 降至 15，退出后 1s 恢复 |
| 离席省电 | 10fps 下 CPU 占用较 60fps 下降 ≥50% |
| 隐私 | 抓包验证无按键内容外传 |

## 10. 待确认

1. **WORK 态的反应强度**想要「安静陪伴」还是「明显互动」？这决定打字/切窗反应的频率上限。
2. **是否允许角色「吐槽」用户的操作**（如检测到深夜还在打字 → 说一句"该睡了"）？这会引入低频 LLM 调用，成本与体验收益需权衡。
3. Android 的 `UsageStatsManager` 特殊权限是否值得为 WORK 态申请？（用户体验上是一次额外授权弹窗）
