# 动作回执与结果汇报规范

## 1. 两种输出必须分开

Agent 需要区分：

1. **工具层回执**：MCP 返回的 JSON、调度事件和状态快照，是判断执行进度的事实依据。
2. **用户层反馈**：Agent 对实际结果的简短自然语言说明，帮助用户知道发生了什么。

用户层反馈不能覆盖或篡改工具层事实。

## 2. 动作状态的准确解释

| 工具结果 | Agent 应如何理解 | 可以如何向用户表达 |
|---|---|---|
| accepted: true | 已进入调度，不等于播放完成 | “动作已受理，正在执行。” |
| 收到 start | 动作已经开始 | “角色开始执行该动作。” |
| outcome: completed 且有结束回执 | 动作链已正常结束 | “角色已完成该动作。” |
| outcome: interrupted 或 interrupted 事件 | 动作被其他动作打断 | “动作被新的交互打断，没有完整播放。” |
| outcome: pending | 当前调用返回时尚未确认结束 | “动作已开始/受理，完成状态仍在等待回执。” |
| priority-blocked | 当前优先级不允许执行 | “当前有更高优先级动作，暂未执行。” |
| conflict / start-rejected | 动作启动失败或被状态机拒绝 | 说明冲突或拒绝原因，不得说已完成 |
| already-open / already-closed | 目标状态已经成立，动作被正常跳过 | “角色已经处于目标姿势。” |

具体字段以当前工具返回为准；如果某个字段缺失，不要补造。

## 3. 用户可见反馈模板

优先采用短句：

- **已完成**：已让角色转向你，并完成了待机姿势调整。
- **执行中**：角色已开始执行挥手动作。
- **已受理但未确认**：动作已进入队列，完成状态还在等待回执。
- **被打断**：挥手动作被后续交互打断，没有完整播放。
- **失败**：动作未能启动：当前动作与正在播放的手臂动作冲突。
- **能力不足**：当前 MCP 工具没有直接控制关键帧的能力，因此无法执行这段自定义动画。

不要把工具原始 JSON 全量展示给普通用户。调试请求除外。

## 4. 关联请求与回执

- 对于 l2d_act，保留工具返回的 callId、runId、source、events 等字段（如果存在）。
- 将 start、end、interrupted 视为同一动作运行过程中的不同事件。
- 不要把 callId 或 runId 改写成不存在的通用 requestId。
- 如果宿主未来新增统一请求封套，应由宿主生成并传递关联 ID；在该能力实际落地前，Agent 不得声称已支持。
- 对于非 l2d_act 工具，按该工具自身 schema 和返回结构处理，不要套用不存在的事件字段。

## 5. 推荐的内部动作记录

以下是 Agent 内部组织执行结果的建议结构，不是当前 MCP 新增的返回 schema：

~~~text
Action report
- intent: 用户希望达成的目标
- workspace_context: 实际读取且与动作相关的上下文摘要
- planned_actions: 实际调用的工具和动作目标
- execution_status: completed | executing | interrupted | rejected | failed | unknown
- evidence: 工具返回的状态、回执或错误原因
- user_summary: 一句简短、准确的用户反馈
- follow_up: 是否需要继续动作或询问用户
~~~

## 6. 汇报原则

- 只报告真实调用过的动作。
- 区分计划、已受理、已开始和已完成。
- 简短结果只描述最重要的变化，不复述全部上下文。
- 如果工作区状态仅提供标题、Session 状态和活动时长，就只能按这些信息汇报；不能推断文件、命令或聊天内容。
- 没有验证证据时，明确说明结果待确认。
