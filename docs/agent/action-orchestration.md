# 动作编排与能力组合

## 1. 编排目标

将用户的自然语言意图转化为一组**有依据、可执行、可验证、可解释**的 Live2D 动作。

动作编排不是把所有工具都调用一遍，而是选择能够达成目标的最小动作集合。优先复用已有 MCP 工具和引擎状态机，不为每个新意图创造专用 API。

## 2. 先识别意图类型

| 意图 | 优先考虑的能力 |
|---|---|
| 表达情绪 | l2d_emote 或 l2d_set_expression |
| 播放单个预设动作 | l2d_play_motion |
| 调整手部姿势 | l2d_set_pose |
| 改变注视方向 | l2d_gaze |
| 显示一句角色气泡 | l2d_say |
| 执行多阶段表现 | l2d_act |
| 查询当前角色状态 | l2d_get_state |
| 恢复角色状态 | l2d_reset |
| 确保/检查专属工作区 | l2d_workspace_ensure / l2d_workspace_status |

不要仅凭名称猜测参数。调用前必须参考当前工具 schema。

## 3. 七步动作推理循环

### Observe — 观察

读取与请求直接相关的状态。只有当当前状态会影响动作选择、冲突判断或用户明确要求结合工作区情况时，才查询状态。

### Understand — 理解

将请求拆分为：
- 用户最终想看到什么；
- 需要改变角色的哪些维度（表情、动作、姿势、注视、气泡）；
- 是否依赖工作区状态；
- 是否存在动作持续时间、顺序或互斥要求。

### Discover — 发现

查找当前可用工具、参数 schema、文档限制和状态机规则。区分 MCP 工具与仅存在于浏览器运行时的接口。

### Compose — 编排

确定动作集合、顺序、依赖、优先级和结束条件。尽可能用一次 l2d_act 表达一段连贯的动作链；简单请求直接使用单个工具。

### Execute — 执行

只调用计划中必要的工具。不要并发发送相互冲突的动作，也不要在工具尚未返回时假设执行结果。

### Verify — 验证

根据工具返回的 accepted、reason、events、outcome 和必要时的 l2d_get_state 判断动作是否开始、完成、被打断或仍在等待。

### Report — 汇报

向用户说明实际发生的动作、简短结果和未完成事项。不要暴露原始 JSON，除非用户明确要求调试信息。

## 4. 动作组合模式

### 4.1 单动作

适用于意图明确且只需要改变一个维度的请求。

示例：用户说“看着我”。

- 检查当前 Session 是否提供 l2d_gaze。
- 按工具 schema 使用中性/正前方坐标。
- 根据返回值确认请求已被接受。
- 不额外叠加无关表情或动作。

### 4.2 顺序动作链

适用于动作之间存在明确先后关系的请求。

示例：用户要求“先思考一下，再给我回应”。

- 选择文档支持的 thinking 阶段；
- 等待该动作链的实际回执；
- 再根据后续对话进入 speaking 或其他适当阶段。

优先使用 l2d_act 已文档化的 phase（如 listening、thinking、speaking、settle），不要自行发明 phase 名称。

### 4.3 条件动作

适用于动作选择依赖当前状态的请求。

示例：用户要求“如果角色还在做动作，就等它结束再挥手”。

- 查询 l2d_get_state；
- 仅依据状态快照中实际存在的字段判断；
- 如果工具没有暴露动作完成事件或等待接口，不得假装能够等待；
- 在状态未知或冲突时，向用户说明限制，或采用安全的非冲突替代方案。

### 4.4 并行动作

并行只适用于互不冲突且工具/调度器明确支持的操作。Live2D 动作、姿势和同一参数通道可能相互覆盖，因此默认采用顺序编排。

不要为了缩短时间而并发提交多个会竞争同一动作槽或同一手臂/姿态资源的调用。若接口没有明确的并行语义，按顺序执行。

### 4.5 上下文感知动作

示例：用户说“我现在忙着写代码，让角色安静陪着我”。

- 先查看可用的脱敏工作区状态；
- 只将实际观察到的状态作为依据；
- 选择低干扰、低频的角色表现；
- 不读取工作区聊天内容或文件；
- 不因“忙着写代码”而假装知道用户正在编辑的文件。

## 5. 已知调度语义

根据 MCP README：

- l2d_act 的优先级为 BACKGROUND、NORMAL、FORCE。
- 低优先级动作不能打断高优先级动作。
- 同级动作可以抢占；动作链的关闭步骤和手臂冲突由引擎调度逻辑处理。
- accepted: true 只表示动作链占上调度槽，不代表已播放完成。
- 事件 action-done 的 phase 包括 start、end、interrupted。
- outcome 可能为 completed、interrupted 或 pending。
- priority-blocked 是被更高优先级动作挡住的正常拒绝结果；不要原样无限重试。
- already-open / already-closed 是正常跳过提示，不应视为失败。
- conflict 和 start-rejected 表示动作没有按计划成功启动。

优先级使用原则：

| 优先级 | 使用原则 |
|---|---|
| BACKGROUND | 仅用于低干扰、可被打断的环境动作 |
| NORMAL | 一般情境反应；不要用来覆盖正在进行的 FORCE 演出 |
| FORCE | 仅用于确有必要的对话/用户交互演出；不能把所有动作都设为 FORCE |

## 6. 不可越过的能力边界

- MCP 没有 l2d_set_parameters 和 l2d_play_keyframes；不得调用或声称调用成功。
- 浏览器运行时的 window.DSH_L2D 不是 MCP 工具。
- 不得猜测模型动作组名称、动作索引、表情名称或参数 ID。
- 不得通过伪造工具返回值来制造成功状态。
- 不得绕过引擎优先级、动作互斥、权限或工作区隔离。
- 对参数可写性有疑问时，以运行时能力和 docs/参数读写对照.md 为准；MCP 不暴露直接参数写入能力。

## 7. 何时需要询问用户

只有在缺失信息会实质影响安全性或结果时才询问，例如：
- 请求可能触发不可逆或影响其他 Session 的操作；
- 目标动作存在多个含义不同的候选，且无法从上下文区分；
- 当前工具能力不足以完成用户要求，且替代方案会改变预期效果。

对于低风险、可逆的角色表现，优先采用文档支持的保守默认值，不要用多轮问题打断用户。
